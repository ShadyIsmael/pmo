# Meetings module

## Current scope

The supported React/Vite frontend at `apps/web-react` provides a global Meetings browser and a Meetings view inside each project. Both share the same list/calendar browser, query logic, and API hooks. The list supports project, status, date range, and title/objective search filters with pagination. The calendar supports month, week, and day modes for the visible range only. Meeting creation is a dedicated full page at `/meetings/new`, including when launched from a project; project URLs and the optional creation query use the public project ID. The request body uses the internal project ID from the resolved project DTO.

## Calendar and list views

The Meetings browser has a segmented Calendar/List toggle. Both views place filters in the same responsive side panel: accessible projects appear in a vertical checkbox list, alongside project search, meeting search, status, and date-range controls. In list view, results and pagination appear beside the panel. In calendar view, the date-range filter narrows results within the visible month/week/day range while calendar navigation and scale controls remain beside the calendar. View, mode, anchor date, project selection, status, search, page, and date range are stored in URL search parameters, so switching views or navigating to a meeting and back preserves the working context.

In both views, projects have individual checkboxes with Select all and Clear all. On the global page, selection defaults to every accessible project; on a project page, the project remains locked and is shown as checked. Meeting queries include only the selected accessible project IDs, including when all are selected, so unprojected meetings are excluded. Selected public IDs are sent through `projectIds` and resolved by the API within the authenticated tenant; returned events are also restricted to the selected projects before rendering. Project options come from the authorized `/api/meetings/projects` endpoint, not from a client-side copy of the project list. The checkbox list renders at most 200 matches and asks the user to refine the search beyond that.

Calendar events show the meeting title, start time, project name and deterministic project colour, and a status icon plus label; the legend repeats project colours and all four statuses, so colour is never the only signal. Clicking an event opens the existing Meeting Details page, clicking a day switches to a date-scoped day view, and days with more than two month-view events show a `+N more` control. Month, week, and day layouts place overlapping meetings side by side. Calendar queries request only the visible range, use overlap semantics so multi-day meetings appear on each covered day, and show a truncation notice when the server caps the response. Loading, empty, permission-denied, project-load, and retryable error states are localized in English and Arabic, with RTL-safe logical spacing and light/dark tokens.

Project-page URLs and list filters use the tenant-scoped public project ID. Meeting create/update request bodies use the internal project ID from the loaded project DTO (`ProjectDto.id`); the server checks that ID against the authenticated tenant and management scope. Project Governance preserves the public ID in the URL and passes the resolved internal ID only in the request body. Creation saves the meeting, participants, and initial ordered agenda in one EF save operation.

Meeting records store an organizer and internal or external participants. Status follows `Scheduled → InProgress → Completed`; a scheduled meeting may also be cancelled. Dedicated start/end endpoints record server UTC actual timestamps and actor audit entries. Generic edits cannot start or complete meetings, and a started meeting's agenda is read-only in the service and UI. Completed details show scheduled and actual times; actual duration is derived from the recorded timestamps. Invitation responses and actual attendance are distinct fields. The workspace does not expose RSVP controls. Attendance is recorded only while the meeting is in progress and is read-only after completion.

The workspace is lifecycle-based. A Scheduled meeting shows information, organizer/invitees, schedule, agenda, and scheduled-meeting controls only. An In Progress meeting shows actual start, read-only agenda, attendance, decisions, and action items; Work Item controls and Minutes remain hidden. Action items may be associated with an agenda topic. A Completed meeting shows scheduled and actual timestamps, final agenda, attendance, decisions, action items, Work Item linking/creation, and the Minutes editor/publication/comments workspace. The Minutes route and its comments, attachments, checklist, and Work Item-link endpoints reject access until completion. Action-item list and edit operations are available only after start; linking/unlinking Work Items is restricted to completed meetings. Action items are ordered by due date, with undated items last, and overdue unfinished items are highlighted. During In Progress, a dedicated decisions API stores the decision text in the existing `MeetingMinutes.Decisions` field without exposing the Minutes editor. After completion, the Minutes editor supports draft save and finalization, including summary, discussion notes, decisions, outcomes, threaded comments, follow-up checklist, attachments, and links to Work Items. The Project Overview KPI compares meetings with final minutes against meetings without final minutes.

## Manual meeting sharing

The completed meeting's **Minutes & Follow-up** tab has a Share side sheet with two independent, explicit operations. **Share minutes by email** is available only for Final minutes. The sender can select internal attendees whose actual attendance is Present or Late, or search all active internal users in the same tenant regardless of project association. The attendee shortcut excludes Absent and Excused people; those users remain findable in the all-users group. Every recipient must have an active same-tenant account; email recipients also require a valid address, the `MeetingMinutesShared` email preference, and a configured shared email provider. External addresses are not accepted. A rendered preview of the exact published minutes fields and follow-up actions is shown before a second explicit confirmation.

The email request snapshots the final Minutes version, meeting/project/date/organizer details, decisions, outcomes, and follow-up actions into the canonical Notification body before it is queued. It includes a secure authenticated application link. Later changes to meeting minutes do not rewrite the queued message. The shared SMTP adapter renders a safe HTML view with a plain-text alternative. A deterministic notification ID derived from tenant, actor, request ID, operation, and recipient makes client retries idempotent; a new request ID permits intentional resends. Sharing history reads Notification and NotificationDelivery records without returning minutes content. Email `Pending` means queued or retrying; `Sent` means the SMTP provider accepted the message, not that it reached an inbox or was read.

**Notify meeting completion** separately creates an in-app notification for sender-selected active users in the same tenant. The meeting must still be associated with a project. The notice contains only the meeting title, project, completion time, and secure link; minutes content is excluded. The operation is manual and selects nobody by default. Each user's `MeetingCompleted` channel preferences are honored, so explicitly enabled email or push channels may also be queued by the shared Notifications service. The sharing API requires `Meeting.Manage`, completed meeting state, same-tenant active recipient validation, and audit entries.

The existing Notifications and NotificationDeliveries tables hold the operation and history; no database migration is required. Manual minutes email uses the opt-in `MeetingMinutesShared` email preference and disables push and in-app copies. Completion notification delivery respects that event's existing in-app/email/push preferences. Configure `Meetings:Sharing:ApplicationBaseUrl` (environment variable `Meetings__Sharing__ApplicationBaseUrl`) to the trusted HTTPS application base URL. Development may use HTTP only for a loopback URL. SMTP provider settings and secret handling are documented in [`docs/integrations/email-notifications.md`](../integrations/email-notifications.md). External attendee delivery remains disabled.

Completed meeting details use two tabs: **Minutes & Follow-up** is the default and contains the minutes collaboration/editor and action items; **Meeting Details** contains meeting information, scheduled/actual times, organizer/participants, agenda, and read-only attendance. The selected details tab is addressable with `?tab=details`; omitting the tab parameter opens Minutes & Follow-up. Ending a meeting clears any tab selection so the newly completed meeting opens on Minutes & Follow-up. Both tab panels remain mounted while hidden, preserving unsaved minutes, comment, checklist, and action-item input state during tab switches. Scheduled and In Progress views keep their lifecycle-specific layouts.

Attendance records actual participation as `Present`, `Late`, `Excused`, or `Absent`; invitation responses remain `Pending`, `Accepted`, `Declined`, or `Tentative` in their separate field. The organizer can update attendance through the organizer-scoped endpoint, which also verifies organizer identity server-side. Users with `Meeting.Edit` can use the editor endpoint. The API preserves the legacy `attendanceStatus` projection for older clients, but new clients should use `invitationResponseStatus` and `actualAttendanceStatus`.

## Creation page

The dedicated Create Meeting page uses the available app workspace width. Meeting information, schedule and reminders, people, and agenda are grouped into responsive cards that stack on narrow screens and form a two-column layout on desktop; very wide workspaces use balanced section spans. The agenda editor/list and participant selections adapt to content growth without fixed page heights. Meeting duration can be selected in 15-minute steps from 15 minutes through eight hours; choosing a duration updates the end date/time, while editing the end date/time displays the calculated duration (including custom durations). The duration explanation is available from a keyboard-accessible info tooltip beside the duration label. Duration is derived from the start/end timestamps and is not sent as a separate field. The meeting link is optional: blank input is omitted from the request and stored as null; a supplied link must use an absolute HTTP or HTTPS URL. Form validation and lookup/save errors are summarized in an alert at the top of the form, including agenda and recurrence errors. English and Arabic labels use the centralized catalogs, and the layout uses logical spacing/direction-aware controls.

Meeting type remains an API-contract dependency: the frontend `MeetingInput` and backend `CreateMeetingRequest` do not expose `MeetingType`, so the create page does not offer a selector that could not be persisted. Add an explicit request/response mapping before making meeting type editable. No backend or database changes were made for this page update.

## Action item and Work Item relationship

Meeting action items can link to an existing same-tenant Task or Issue in the same project, or create a Task through the existing Work Items API and link it. An action may also reference an Agenda item from its own meeting; the service validates that parent relationship. Work Item creation, assignment, and workflow transitions remain owned by the Work Items module; Meetings does not copy or replace Work Item functionality. A linked Work Item remains independent if the meeting action is edited or removed. Meeting action status is a separate meeting follow-up status and is not synchronized with the Work Item workflow status. Action items remain editable after meeting completion for follow-up.

Linking requires `Meeting.Manage` and `WorkItem.View`; creating a linked Task also requires `WorkItem.Create`. The server checks the Work Item tenant, meeting project, and management scope before linking. The action list includes the linked Work Item title only for callers with `WorkItem.View` and matching tenant/project scope. The optional `MeetingAction.WorkItemId` relationship uses a nullable foreign key to Work Items with an index and clears the link if a Work Item is physically deleted. A soft-deleted Work Item can remain linked until an authorized meeting manager removes the reference. `MeetingAction.AgendaItemId` is nullable and indexed; agenda removal clears action references in the service, with a `NO ACTION` database FK to avoid SQL Server multiple-cascade paths.

## Access and data boundaries

Meeting APIs require the corresponding `Meeting.View`, `Meeting.Create`, `Meeting.Edit`, `Meeting.Delete`, or `Meeting.Manage` permission. Meeting reads and writes use tenant query filters and management-scope checks. Meeting child routes are checked against the parent meeting and its owning project by `ProjectResourceScopeMiddleware`. Self-attendance is restricted to the signed-in participant and invitation-response states; final attendance states require `Meeting.Edit`.

## Reminder delivery

`MeetingReminderScheduler` reconciles reminder dispatches for all tenants and delivers canonical notifications to internal participants and the organizer. It records the dispatch and notification entries in one database transaction, using the dispatch row version to avoid duplicate reminder dispatches from competing application instances. The shared Notifications service creates at most one delivery row per notification and channel; the shared worker leases and retries Email and Push deliveries. Push requires recipient preference plus Firebase configuration. Email requires recipient email preference plus the shared SMTP provider configuration described in [`docs/integrations/email-notifications.md`](../integrations/email-notifications.md).

Reminder text is bilingual in one message because user locale is stored in browser preferences rather than the user profile. External attendee email reminders are not enabled; sending meeting details to an external address needs an explicit recipient-policy authorization. Email delivery depends on deployment SMTP configuration and cannot be considered verified until the owner tests a real provider. SMTP retries can resend a message when provider acceptance is ambiguous; scheduler dispatch and delivery-row deduplication prevent duplicate queued reminders but cannot guarantee exactly-once delivery by SMTP.

Migration `20261028130000_AddMeetingLifecycleTracking` adds nullable actual start/end timestamps and the optional action-to-agenda link, index, and `NO ACTION` foreign key. Migration `20261028150000_SeparateMeetingInvitationAndAttendanceStatuses` adds nullable `MeetingParticipants.InvitationResponseStatus`; it migrates legacy invitation values out of `AttendanceStatus` and converts legacy `Attended` values to `Present`. These additive changes preserve participant and meeting-action rows. The current model snapshot and the new migration target model include the invitation-response column. The migration has not been applied; no database was accessed or written for this lifecycle refinement. Rolling the new migration down after both fields have been populated necessarily collapses the two statuses back into the legacy column, retaining actual attendance when present and otherwise retaining the invitation response.

Email delivery reuses the existing `NotificationDeliveries` Email channel and `NotificationPreferences.EmailEnabled` field. It requires no notification-schema migration. No migrations were applied and no database was written.
