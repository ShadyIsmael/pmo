## Workflow findings

### 1. Create User without a role

`POST /api/users` is protected by `Users.ManageAccounts`; the service requires that permission, checks `Users.AssignRoles` only if a role list is supplied, binds to authenticated Tenant context, validates the request and role set before saving, and writes audit information (`UsersController.cs:285-304`; `UserAdministrationService.cs:106-145,150-190`). This is a coherent source-level path. Runtime behavior and persisted atomicity were not observed.

### 2. Protected Tenant Admin → Create User → Assign Project Manager

The desired journey requires `Users.ManageAccounts`, `Users.AssignRoles`, a different target user, an eligible Project Manager role, and a protected `tenant.admin` actor. The service checks all current target-role permissions. But the seed classifies Project Manager as a System Role; for an unheld ordinary permission the current code rejects `role.IsSystem` at `UserAdministrationService.cs:562-565` before reaching the protected-Tenant-Admin delegation allowance at `:568-573`. The PM role must first satisfy the approved Non-System classification and identity design. The source therefore does not establish the required end-to-end success.

The latest source attachment §4.3 reports an observed `POST /api/users` 403 with trace `0HNQ2H5VM306U:00000001`, but explicitly says the rejected key/reason and deployed assembly are unverified. The older `USER-CREATION-403-ROOT-CAUSE-AND-FIX.md:4-8,19-28` also says runtime/test verification is pending. The current source has the System-role rejection path before the protected-admin ordinary-delegation allowance (`UserAdministrationService.cs:562-573`), which is a static conflict and a plausible cause, not a trace-confirmed historical root cause. No independent trace was captured in this review and no successful PM assignment is evidenced.

### 3. Role selection lookup versus assignment authority

The user page shows role choices when the actor has `Users.AssignRoles` and calls `useAssignableRoles` (`AccessPages.tsx:68-75`; `administration/api/admin.ts:110-115`). That hook uses `/api/roles/manage`; the route requires `Roles.View` (`RolesController.cs:37-43`). The `Users.AssignRoles` catalog entry depends on `Users.View`, not `Roles.View` (`PermissionCatalog.cs:915-919`). A user with the documented role-assignment authority but no `Roles.View` can reach a role picker whose lookup receives 403. This violates the least-privilege lookup expectation. The endpoint name/DTO also indicates manageable roles and includes management counts, rather than explicitly returning the minimal assignable set. Mutation-side full validation must remain authoritative even after a lookup is corrected.

The related hypothesis that `Roles.Create`/`Roles.ConfigurePermissions` action-only actors lack a view permission was **not retained as a confirmed gap**: the catalog makes those actions depend on `Roles.View` (`PermissionCatalog.cs:1041-1063`), and effective permissions enforce dependencies (`UserEffectivePermissionService.cs:81-89`).

### 4. Assign an existing role / edit user assignments

`CanAssignRolesAsync` is shared by new-user creation and existing-user role changes. It checks actor identity and Tenant, validates the selected role and every current grant, denies the protected Admin role itself, rejects invalid/reserved/inactive/unassignable/restricted grants, prevents self-escalation, and applies delegation authority (`UserAdministrationService.cs:470-594`). Existing-user updates also block self-role changes and require `Users.AssignRoles` when the role set changes (`:312-339`). The controller requires `Users.View`, which is the declared dependency for `Users.AssignRoles` (`UsersController.cs:330-346`; `PermissionCatalog.cs:915-919`). Create/update payloads resolve selected roles from display-name strings (`UserAdministrationService.cs:452-467`), so a later API contract should use stable role IDs while continuing to revalidate Tenant and the full grant set server-side.

Existing test **source** in `AdminDelegationAuthorityRecoveryTests.cs:209-228` covers denying a generic System Role and does not establish the required Tenant Admin → unheld Project Manager success. Other test source mentions are not execution evidence.

### 5. Configure, grant and revoke role permissions

Custom role creation sets `IsSystem=false`; category validation, permission IDs, catalog activity, assignability, scope, permission dependencies, and delegation authority are evaluated by `RoleAdministrationService` (`:156-205,497-539`). Update re-reads actor authority under the tenant mutation guard, protects the Admin Core, prevents self-escalation for an assigned custom role, retains role-management access, audits changes, and saves the permission-set replacement (`:231-349`). Delete is a soft delete only for non-System roles with no assigned users; System roles cannot be deleted (`:402-424`).

These paths still use `IsSystem` as a proxy for name/category editing, permission delegation, and deletion. A future implementation needs explicit policies for System, Protected, Assignable, and Editable behavior. `Role` has no `IsActive` property, and no separate role deactivate/reactivate path was found.

### 6. Direct Allow, Deny and Inherit

The backend checks `UserPermissions.Manage`, tenant-binds the target and permission, blocks self-overrides and protected-core Denies, validates permission eligibility and delegation, audits changes, and checks last-effective-admin invariants (`UserAdministrationService.cs:648-803,829-884`). Effective calculation unions role grants and direct Allows, removes Denies, then reapplies the mandatory protected Admin Core and enforces permission dependencies (`EffectivePermissionResolver.cs:13-29`; `UserEffectivePermissionService.cs:35-89`).

The React UI conflicts with the backend delegation rule: it enables a permission control only if the actor personally holds the key and globally disables Save if an existing unheld override is present (`AccessPages.tsx:326-328,389-413`). This prevents a protected Tenant Admin from using the backend's possession-independent ordinary direct-override delegation through the UI. The UI's `ManageOverrides` constant maps to `UserPermissions.Manage` (`apps/web-react/src/lib/permissions.ts:145-146`), so the endpoint permission name itself is aligned.

### 7. Effective access, scope and cross-module dependencies

The effective permission service filters users, memberships, roles, permissions and overrides by Tenant and deletion/active state (`UserEffectivePermissionService.cs:19-63`). A permission key does not grant ownership or resource membership; consumers must still resolve Organization/Project/resource scope, as the earlier decision register requires (`DECISION-REGISTER.md:27-29`).

Project Manager classification also interacts with workflow lookup: `UsersController.GetProjectManagerCandidates` searches users assigned to the `Management` role category and filters on `Handover.Approve` (`UsersController.cs:54-67`). Reclassification must preserve the Project Manager's Management category unless a separately approved domain rule changes it. Category remains descriptively distinct from System classification and grant eligibility.

### 8. Role identity and Organization Admin scope

`Role` stores Tenant identity, name, category, `IsSystem`, and nullable immutable `SystemRoleKey`; `UserRole` stores a Tenant-scoped user/role link, with no Organization ID (`Role.cs:5-35`; `UserRole.cs:5-11`; `User.cs:5-20`). `Organization Admin` was not found in the inspected seed. If it means administration over one specific Organization, the authoritative Organization membership/assignment mechanism and boundary must be identified; do not infer scope from role category or System status.

## Workflow integrity conclusion

The source contains meaningful guards for role grants, self-escalation, Tenant isolation, Active Deny, Protected Core, and last-admin preservation. The principal end-to-end gaps are the seed/System classification conflict for Project Manager, the role-picker lookup gate, and the direct-override UI/backend mismatch. Organization Admin scope is not established in inspected identity models. All findings are static and based on a heavily modified worktree; no tests, database queries, runtime requests, or browser UAT were run.

### P0 journey: Protected Tenant Admin → Create User → Assign Project Manager → Success

**Required expected result:** a protected Tenant Admin with user-account and role-delegation authority can create an active same-Tenant user and assign the eligible ordinary Project Manager role, even if the Admin has none of the Project Manager's operational permissions. Assignment must not add operational permissions to the Admin or bypass the catalog, scope, Protected Core, Tenant Isolation, Active Deny, or self-escalation protections.

The current source has these gates:

1. `POST /api/users` is protected by `Users.ManageAccounts`. When roles are supplied, the service separately requires `Users.AssignRoles` and rechecks both under the Tenant Admin mutation guard (`UsersController.cs:289-304`; `UserAdministrationService.cs:159-176`).
2. The chooser obtains `/api/roles/assignable`, protected by `Users.AssignRoles` rather than `Roles.View` (`RolesController.cs:37-45`; React `AccessPages.tsx:75`).
3. The service identifies protected Tenant Admin through role membership and passes that identity to the shared role assignment policy (`UserAdministrationService.cs:550-589,626-630`). The policy skips actor-possession as a blocker for a protected Admin only after the role and each permission have passed identity, Tenant, catalog, assignability, scope, restriction, dependency, and self-escalation checks (`RoleAssignmentAuthorizationPolicy.cs:46-103`).
4. User creation writes User and UserRole membership, writes an audit entry, saves, and commits under its mutation guard (`UserAdministrationService.cs:203-249`).

**Reported `POST /api/users → 403`: root cause is not confirmed.** Current controller/service code has several independent 403 gates: caller lacks `Users.ManageAccounts`, caller lacks `Users.AssignRoles` while roles were included, permission was revoked before the guarded operation, actor identity/Tenant context is invalid, protected Tenant Admin detection does not match persisted UserRole/RoleKey state, or selected role/permission fails delegation checks. A role-policy rejection is logged with reason code, actor, Tenant, target, role classification/keys, permission key/scope, and restricted/assignable state (`UserAdministrationService.cs:597-623`); the controller response itself is generic. Investigation must correlate the original request trace with that structured log and inspect the active deployed artifact and database state before attributing the failure.

**Downstream Project assignment is a separate authority transition.** `CreateProjectSheet` only offers an initial manager when the actor has `Handover.AdminInitiate` and a writable context; the manager lookup uses `WorkflowLookup.Handover.ManagerCandidates` and returns active Management-category users with effective `Handover.Approve` (`CreateProjectSheet.tsx:174-202`; `UsersController.cs:138-154`). `ProjectService` requires a matching authenticated actor, same-Tenant active candidate, Management-category role, and effective `Handover.Approve` (`ProjectService.cs:209-226,744-760`). The Project Manager role seed includes `Handover.Approve` (`SeedDataProvider.cs:2588`), so it can qualify; the candidate rule is not exclusive to that RoleKey. After Project creation, the UI treats the manager field as read-only and routes changes through Handover (`CreateProjectSheet.tsx:599-614`). User role assignment does not itself appoint that user to any Project.
