# Project Settings Permission Matrix

**Updated:** 2026-11-04  
**Scope:** Unified Project Header Settings Side Sheet containing General Settings, Workflow & Approval Configuration, Financial Approval Settings, and Annual Budget Approval Defaults, with their APIs and permission boundaries.

## Canonical permissions

| Permission | Level | Scope | Roles & Permissions location | Dependency / intent |
|---|---|---|---|---|
| `ProjectSettings.View` | View | Project | Projects → Settings | Opens Project Settings in the authenticated Tenant and authorized Project scope. It does not grant access to a section whose own View permission is missing. |
| `ProjectSettings.Edit` | Action | Project | Projects → Settings | Requires `ProjectSettings.View`. Allows editing general Project Settings only when the operation's own protected permission is also present. |

The catalog supplies English and Arabic names, descriptions, and screen grouping. The permission pair has no legacy alias and is not part of the dynamic Tenant Administration baseline because both entries are Project-scoped. The stable `tenant.admin` system role receives them as narrow additive grants through the existing identity seed/reconciliation path. This is tied to immutable system-role identity; the `pmo.admin` display name or any other role name does not provide access. The additive path preserves unrelated grants and leaves explicit user Deny overrides for these Project-scoped permissions unchanged.

`Project.Edit` remains the protected operation permission for changing Project master data in General Settings. In the consolidated Side Sheet, that edit requires `ProjectSettings.View`, `ProjectSettings.Edit`, `Project.Edit`, Project scope, and a mutable context. A Project.Edit-only actor retains the existing separate project edit action but does not gain Settings Side Sheet access. Workflow configuration, financial settings, and approval defaults each keep their own section and operation permissions below.

Existing supporting permissions remain separate and are not duplicated: `Workflow.View` authorizes published workflow-definition choices inside Workflow & Approval Configuration; `ProjectAnnualBudget.View` and `ProjectFinancialFoundation.View` control their respective financial sections; and the critical `ProjectAnnualBudget.ManageApprovalConfiguration` remains required for persistent financial configuration saves. `ProjectApproval.Override` applies to one submission and never updates saved defaults. `Workflow.View` does not grant Project Settings access or bypass the Project Settings View/Edit pair.

## Protected Admin and Deny behavior

The protected Tenant Admin remains identified by `Role.SystemRoleKey = tenant.admin`. The two Project-scoped grants are supplementary, additive seed grants rather than dynamic Tenant Administration baseline members. The seed source targets stable Admin identity, adds only missing Project Settings grants, and preserves unrelated role grants and user-level Deny decisions; `pmo.admin` does not receive access by display name. A Deny for `ProjectSettings.View` or `.Edit` remains effective because these keys are outside the mandatory Tenant Admin baseline.

The current resolver applies Active Deny after ordinary role/direct Allow grants. The Settings keys and `ProjectAnnualBudget.ManageApprovalConfiguration` are outside the mandatory tenant Admin baseline, so a Deny on these keys remains effective. Current targeted API tests passed the Active Deny, scope, and authorized one-time override scenarios. Fresh Admin seeding no longer adds Annual Budget View/Create/EditDraft/Submit grants; ordinary reseeding preserves existing grants and financial history. The verified Development database currently has three role grants for `ProjectAnnualBudget.View` (including the existing Admin and Project Manager role grants) and none for `ProjectAnnualBudget.ManageApprovalConfiguration`; direct Allow/Deny rows for both keys are zero. No `ProjectAnnualBudget.Approve` or `ProjectApproval.Override` role/direct Allow grants exist. Existing View grants were preserved, and this closure made no permission-data writes.

The secure initial View/Manage delegation path is now source-defined. It requires the actor's effective `Roles.ConfigurePermissions` and `TenantAdministration.ManageScope`, honors Active Deny, permits a custom role or a different same-tenant user, rejects self-assignment and new grants to system roles, and preserves unrelated grants. It does not delegate `ProjectAnnualBudget.Approve` or `ProjectApproval.Override`; `ProjectPaymentRequest.Approve` also has no persisted grant and no first-grant delegation path. The protected `tenant.admin` role and an active member have the two delegation prerequisites, but the database has no approver grant; no approver recipient was authorized or provisioned in this closure.
